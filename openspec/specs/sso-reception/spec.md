# SSO Reception Specification

## Purpose

Defines how the TPV receives, validates, and consumes SSO tokens generated by the PrestaShop `tpvconnect` module to authenticate pre-configured users via PHP native sessions.

## Token Format

`base64url(json_payload)~hmac_hex` where `json_payload` = `{employee_id: int, shop_id: int, timestamp: int, nonce: string}` and `hmac_hex` = HMAC-SHA256 of the base64url-encoded payload using `SSO_SHARED_SECRET`.

## Requirements

### Requirement: Token Verification Service

`SsoTokenVerifier` SHALL validate SSO tokens by verifying: (1) format contains exactly two `~`-separated parts; (2) HMAC-SHA256 signature matches using `SSO_SHARED_SECRET`; (3) timestamp is within 60 seconds; (4) nonce has not been consumed. Verification order MUST follow the sequence above — early rejection on each step.

#### Scenario: Valid token passes all checks

- GIVEN a token with valid format, correct HMAC, timestamp within 60s, and unused nonce
- WHEN `SsoTokenVerifier::verify()` is called
- THEN it returns a verified payload containing `employee_id`, `shop_id`, `timestamp`, `nonce`
- AND the nonce is recorded as consumed

#### Scenario: Invalid token format — no tilde separator

- GIVEN a token string without the `~` separator
- WHEN `SsoTokenVerifier::verify()` is called
- THEN it returns a format error

#### Scenario: HMAC signature mismatch

- GIVEN a token with a signature that does not match the recomputed HMAC
- WHEN `SsoTokenVerifier::verify()` is called
- THEN it returns a signature error

#### Scenario: Expired timestamp

- GIVEN a token with a timestamp older than 60 seconds from current time
- WHEN `SsoTokenVerifier::verify()` is called
- THEN it returns an expiry error

#### Scenario: Replayed nonce

- GIVEN a nonce already present in the `sso_nonce` table
- WHEN `SsoTokenVerifier::verify()` is called
- THEN it returns a replay error

### Requirement: SSO Controller

`SsoController` at `GET /sso` SHALL accept a `token` query parameter, delegate validation to `SsoTokenVerifier`, create a PHP native session on success (with `session_regenerate_id()`), persist authenticated user context for downstream APIs, and redirect to `/app/pos`. The PHP session MUST carry `shop_id` and MUST initialize cash-context keys for `terminal_id` and `cash_session_id` so later cash APIs can resolve or update them.

#### Scenario: Successful SSO authentication

- GIVEN a valid, unexpired token for a known employee
- WHEN GET `/sso?token={valid_token}` is requested
- THEN a PHP session is created with authenticated user data, `shop_id`, and initialized cash-context keys
- AND the session ID is regenerated
- AND the user's `last_login_at` is updated
- AND the response redirects to `/app/pos`

#### Scenario: Missing token parameter

- GIVEN a request to GET `/sso` without a `token` parameter
- WHEN the controller processes the request
- THEN it returns HTTP 400 with message "Missing token"

### Requirement: User Lookup

The system SHALL look up TPV users by `ps_employee_id` from the verified token payload. Only pre-configured users are permitted; unknown employees MUST receive a clear error.

#### Scenario: Known employee

- GIVEN a verified token with `employee_id` matching an existing TPV user's `ps_employee_id`
- WHEN the system performs the lookup
- THEN it returns the user record including `id`, `name`, and `role_id`

#### Scenario: Unknown employee

- GIVEN a verified token with `employee_id` not found in the TPV `user` table
- WHEN the system performs the lookup
- THEN it returns HTTP 403 with message "User not configured"

### Requirement: Nonce Storage

The system SHALL store consumed nonces in a `sso_nonce` database table with `nonce` (primary key) and `consumed_at` (datetime) columns. The system MUST auto-delete nonces older than 120 seconds on each verification call, before the uniqueness check.

#### Scenario: Nonce stored on first use

- GIVEN a valid token with a new nonce
- WHEN verification succeeds
- THEN the nonce is inserted into `sso_nonce` with the current `consumed_at` timestamp

#### Scenario: Replayed nonce detected

- GIVEN a nonce already present in `sso_nonce`
- WHEN verification checks for nonce existence
- THEN the system rejects the token without inserting a duplicate

#### Scenario: Expired nonces auto-cleaned

- GIVEN `sso_nonce` contains entries with `consumed_at` older than 120 seconds
- WHEN `SsoTokenVerifier::verify()` is called
- THEN all entries older than 120 seconds are deleted before the uniqueness check runs

### Requirement: Error Handling

The SSO flow SHALL produce the following HTTP responses:

| Condition | Status | Message |
|-----------|--------|---------|
| Missing token parameter | 400 | Missing token |
| Token format invalid | 400 | Malformed token |
| HMAC signature invalid | 401 | Invalid token signature |
| Timestamp expired (>60s) | 401 | Token has expired |
| Nonce already consumed | 401 | Token already used |
| Employee not configured | 403 | User not configured |
| SSO secret misconfigured | 500 | SSO configuration error |

#### Scenario: Invalid signature returns 401

- GIVEN a token whose HMAC does not verify
- WHEN GET `/sso?token={bad_sig_token}` is requested
- THEN the response is HTTP 401 with message "Invalid token signature"

#### Scenario: Unknown user returns 403

- GIVEN a valid token with an unmapped `employee_id`
- WHEN GET `/sso?token={token}` is requested
- THEN the response is HTTP 403 with message "User not configured"

#### Scenario: Misconfigured secret returns 500

- GIVEN `SSO_SHARED_SECRET` is empty or unset
- WHEN any SSO request is processed
- THEN the response is HTTP 500 with message "SSO configuration error"

### Requirement: Configuration

The system SHALL read `SSO_SHARED_SECRET` from the environment variable. This value MUST be identical to the `TPVCONNECT_SSO_SECRET` in the PrestaShop `tpvconnect` module. The secret MUST NOT be empty at runtime.

#### Scenario: Shared secret is properly configured

- GIVEN `SSO_SHARED_SECRET` is set to a non-empty value matching the PS module
- WHEN `SsoTokenVerifier` validates a token
- THEN it uses this secret to compute and verify the HMAC

#### Scenario: Shared secret is missing or empty

- GIVEN `SSO_SHARED_SECRET` is unset or an empty string
- WHEN the SSO controller is invoked
- THEN it immediately returns HTTP 500 without processing the token
