# Proposal: SSO Token Reception and Authentication (TPV Side)

## Intent

Enable PrestaShop Back Office employees to seamlessly authenticate into the TPV via a signed, single-use SSO token generated by the `tpvconnect` module.

## Scope

### In Scope
- `SsoTokenVerifier` service: HMAC-SHA256 validation, timestamp ≤60s check, nonce replay prevention
- `sso_nonce` DB migration and repository (consumed nonce tracking)
- `SsoController` implementation: validate token → lookup user by `ps_employee_id` → create PHP native session → redirect to dashboard
- `SSO_SHARED_SECRET` env var and parameter configuration
- Error handling for invalid, expired, replayed, and unknown-user scenarios
- Session check helper for protected routes

### Out of Scope
- Auto-provisioning users from PrestaShop API
- Symfony Security bundle or JWT-based auth
- Role-based access control
- Dashboard/landing page (separate change)
- POST-based SSO or token-in-cookie approaches

## Capabilities

### New Capabilities
- `sso-reception`: TPV receives, validates, and consumes SSO tokens; creates PHP sessions for pre-configured users.

### Modified Capabilities
- None

## Approach

Lightweight PHP native session auth without new dependencies. The TPV mirrors the PS module's token format (`base64url(json({employee_id, shop_id, timestamp, nonce}))~hmac_sha256`) and validates independently using a shared secret. Pre-configured users are looked up by `ps_employee_id`; unknown employees fail with a clear error. Nonces are stored in a dedicated DB table to prevent replay and cleaned up after 120s.

## Affected Areas

| Area | Impact | Description |
|------|--------|-------------|
| `src/Controller/App/SsoController.php` | Modified | Implement full SSO receive/validate/authenticate flow |
| `src/Service/Sso/SsoTokenVerifier.php` | New | Pure PHP token validation with injectable nonce storage |
| `src/Repository/UserRepository.php` | New | DBAL lookup by `ps_employee_id` |
| `migrations/` | New | `sso_nonce` table (`nonce` PK, `consumed_at`) |
| `.env` / `config/services.yaml` | Modified | Add `SSO_SHARED_SECRET` parameter |
| `config/routes.yaml` | Modified | Confirm `/sso` route targets new controller action |

## Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Token payload/format mismatch with PS module | High | Match actual PS module format; add explicit format validation |
| No Symfony Security means manual auth patterns | Medium | Document session pattern; plan Security bundle for Phase 2 |
| Nonce table growth without cleanup | Low | Auto-delete nonces older than 120s on each verification |
| Session management across domains | Low | Both apps on same domain in MVP; document subdomain concerns |

## Rollback Plan

1. Revert `SsoController.php` to placeholder
2. Drop `sso_nonce` table via migration rollback
3. Remove `SSO_SHARED_SECRET` from `.env` and `services.yaml`
4. Clear all PHP sessions (`rm -rf var/sessions/*`)

## Dependencies

- `tpvconnect` PS module installed and configured with `TPVCONNECT_SSO_SECRET`
- `user` table populated with `ps_employee_id` mappings

## Success Criteria

- [ ] Valid SSO token creates PHP session and redirects to dashboard
- [ ] Expired (>60s), invalid HMAC, or replayed nonce returns clear error page
- [ ] Unknown `ps_employee_id` returns "User not configured" error
- [ ] Unit tests cover token validation, nonce replay, and user lookup
