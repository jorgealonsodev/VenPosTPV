# Fiscal journal outside the database (`feat/fiscal-journal`)

Objective: every issued fiscal document is also kept in an append-only journal on the server (outside MySQL) and in the PrestaShop shop, so a database restore can never lose a ticket nor reuse a number. Branch `feat/fiscal-journal`. Delivery: `ask-on-risk`.
Test runners: `.runtime/php-8.5.12/bin/php vendor/bin/phpunit tests/Unit`; real-MySQL integration `tests/Integration` against a disposable `mysql:8.0` docker container (skipped when MySQL is down; a skip is not a pass); `node --test tests/Functional/*.test.cjs`; module `.runtime/php-8.5.12/bin/php vendor/bin/phpunit -c modules/tpvconnect/tests/phpunit.xml`.

## Specs

- S1. Owner: «es que verifactu, no se pueden perder los tickets ni repetir». Every issued document — sale ticket F2 (local sale and coupon sale), credit note R5, full invoice F3 — is appended to the fiscal journal with its fiscal record verbatim (`hash`, `previous_hash`, `generated_at`, number, totals) and the rows needed to rebuild it (Design D2). The journal lives beside the backups (`backups/fiscal-journal/`), folder 0700, files 0600, `.htaccess` deny-all, never under `public/`. Acceptance: after each issuing path (`CheckoutService::createLocalOrder`, `createCouponOrder`, `RefundService::completeLocally` and `::complete`, `InvoiceIssuer::redeem`, and an exchange = R5 + F2) the journal holds exactly one line per document, in chain order, whose `fiscal_record` equals the database row byte for byte. Checks: integration test per path; unit test of permissions and `.htaccess`; `curl` of `/backups/fiscal-journal/` on a served copy returns 403/404.
- S2. Owner, on a journal that cannot be written when selling: «Y si se guarda en algun archivo o en local y cuando vuelva a funcionar se añaden automaticamente?». A journal failure never stops a sale. The TPV tries the second location (`var/fiscal-journal/`); the every-minute task `tpv:cron` appends every missing document from the database, in order, automatically, with no duplicate. Acceptance: with the primary folder read-only, sales succeed and lines land in the secondary; with both read-only, sales succeed and nothing is written; once writable again, one `tpv:cron` run leaves the primary journal complete, ordered, duplicate-free, and the secondary merged. Checks: integration tests with `chmod 0500`; unit test of the merge.
- S3. If the journal stays behind the database for more than 5 minutes there is a warning in Ajustes and one e-mail through the existing backup alert path (`BackupAlertMailer::send`), sent once per incident and again after 24 h if it persists; a recovery clears the warning. Checks: unit tests with a fake clock and a fake mailer; front-end test of the warning text.
- S4. Failure cases of the write protocol (Design D3), each with a test: (a) crash after the intent is written and before commit: no journal line, no block, the intent is resolved as never issued; (b) commit without journal write (process killed after commit): the next flush or the next `tpv:cron` appends it; (c) two tills selling at once: lines in chain order, `seq` without gaps or repeats; (d) a half-written last line: detected, moved aside, rewritten from the database; a damaged line that is not the last one is reported («Diario dañado»), never rewritten; (e) the same document sent twice to the shop: stored once.
- S5. Owner: «es que verifactu, no se pueden perder los tickets ni repetir» (the "repetir" half). After a database restore the TPV detects that the database is BEHIND the journal (or behind what the shop holds) and refuses to issue any document until it is resolved, with a clear message (Design D7). This is what makes a repeated number impossible. Acceptance: restore a dump taken before tickets N+1…N+k; the next sale, coupon sale, credit note or invoice is refused before any number is taken and before any PrestaShop call, with HTTP 423 and the Spanish message; no false block in normal operation (journal behind the database is normal lag, never a block). Checks: integration test with a real dump/restore; concurrency test with flushes and sales interleaved (no false positive in 500 sales).
- S6. Owner: «y como podriamos hacer para que todo lo posterior a la copia si esta bien se mantuviera». A replay re-applies, in order, every document issued after the restored backup, restoring fiscal records verbatim so the chain is continuous: no gap, no duplicate; `FiscalChainVerifier::verify()` is OK afterwards; the counters continue after the last replayed number. Acceptance: dump at ticket 10, sell 11–20 (with a credit note, an invoice, a coupon sale, a cash movement, a transfer payment, an exchange), restore the dump, replay: the database holds 1–20 with the original ids, hashes and totals, the next sale is 21. Checks: integration test; replay interrupted after document 15 (kill) and run again ends identical (idempotent).
- S7. Assumption A1 (recommended, owner may overrule): the replay is a guided administrator action — a button in Ajustes and a console command — never automatic, because a restore may be deliberate. While the guard is active the till cannot sell (A3). The replay restores the documents and what makes them correct (D8); what it does not restore is listed in Ajustes and in the guide (D8.4).
- S8. Owner chose «En la tienda PrestaShop (Recomendado)»: each journaled document is also sent to the shop with the every-minute upload (the outbox) and the module `tpvconnect` stores it; the TPV asks the shop for the last document of each series, so numbers are never repeated even when the server journal is lost. Acceptance: a document reaches the module table once; the TPV's shop head matches the journal head after one `tpv:cron`; a server with an emptied journal and a restored database blocks until the shop confirms or the replay finishes. Checks: module unit tests; TPV integration test with a fake module client.
- S9. A shop without the new module version degrades to the local journal: selling never breaks, the journal uploads wait (no incident, no retry storm), and Ajustes says «Copia en la tienda no disponible: actualiza el módulo TPV Connect a la versión 0.9.0. Mientras tanto el diario se guarda solo en el servidor.» Once the module is upgraded, the waiting documents upload by themselves. Checks: integration test with the client answering 404.
- S10. A restore older than the oldest journal entry kept cannot be replayed: the replay refuses with «La copia restaurada es anterior al diario conservado (desde {fecha}). Restaura una copia más reciente.» and exit code 3, and the guard stays active. Check: integration test.
- S11. Clock and year change: the journal file month, the record's `issue_date`/`generated_at` (Europe/Madrid, as `FiscalRecorder::TIME_ZONE`) and the counter year of the number (`TicketNumberer::next` uses the PHP default zone) may differ at New Year; the journal stores the counter key explicitly and the replay restores that key, never one derived from dates. Check: integration test issuing at 23:30 UTC on 31 December with the PHP zone UTC.
- S12. Project rule «la instalacion instale todo»: a provisioning step creates the folders, writes the journal identity, journals the documents issued before this feature (backfill) and records it in the database; no manual step. Guides: `docs/despliegue-plesk.md` «Copias de seguridad y restauración» updated, new `docs/diario-fiscal.md` (Spanish user guide). Nothing customer-specific anywhere (owner: «esta utilidad actualmente la vamos a usar en clubnatacion, pero puede ser para cualquier tienda en un futuro»): neutral examples only (`tutienda.com`).

Assumptions (owner: «continua con lo que consideres mas optimo»; each is the recommended option, the owner may overrule):
- A1. Replay is guided (button + command), not automatic.
- A2. Replay restores documents and their correct state (D8.2); stock, Z reports, print state and other non-document data are not restored (D8.4).
- A3. While the guard is active the till cannot sell, refund nor invoice. Non-fiscal actions (opening Ajustes, catalog, reports) still work.
- A4. Journal files are never deleted automatically (D10).
- A5. Lag threshold for the warning: 5 minutes; intent timeout: 2 minutes.
- A6. When the journal is lost and the shop cannot confirm (module too old or unreachable), the administrator can start a new journal from the current database with `tpv:fiscal:journal:reset --confirm`, recorded in `audit_log`; it is never done automatically.

## Design

### D1. Where and how it is stored
- Primary: `%kernel.project_dir%/backups/fiscal-journal/` (same rules as `DatabaseBackup::prepareDirectory`: dir 0700, files 0600, `.htaccess` «Require all denied»). Secondary: `%kernel.project_dir%/var/fiscal-journal/` (same rules). `BackupRetention` only deletes names matching its patterns, so the subfolder is safe (assert in a test).
- Files per location: `journal-YYYY-MM.jsonl` (month of `journaled_at`, Europe/Madrid), `journal.id` (`{"journal_id": uuid, "created_at": …}`), `head.json` (last line: `seq`, `number`, `invoice_type`, `hash`, `line_hash`, `fiscal_record_id`), `intents/` (D3), `quarantine/` (damaged tails), `state.json` (D9), `shop-head.json`, `journal.lock` (flock).
- `app_setting` row `fiscal_journal.id` = the journal uuid (table from `VerifactuSettings`/Version00000040). Journal folder without `journal.id` while the setting exists = journal lost (D7).

### D2. Line format (JSON Lines, UTF-8, one document per line, `\n` terminated)
Common fields: `v` (1), `seq` (journal order, 1…n, no gaps), `journaled_at`, `kind` (`F2`, `R5`, `F3`), `series` (`A26`, `R2026`, `F2026`), `counter` (`{"table":"ticket_sequence","letter":"A","year":2026,"number":124}` | `{"table":"credit_note_sequence","year":2026,"number":7}` | `{"table":"invoice_sequence","series":"F","year":2026,"number":3}`), `fiscal_record` (every column including the original `id`, verbatim strings), `rows` (below), `backfill` (true only for D11), `prev` (`line_hash` of the previous line, `""` for seq 1; the first line of a month chains to the last of the previous month), `line_hash` = SHA-256 hex of the canonical JSON (keys sorted, `JSON_UNESCAPED_UNICODE|JSON_UNESCAPED_SLASHES|JSON_PRESERVE_ZERO_FRACTION`) of the line without `line_hash`.
`rows` — full rows as read right after commit (`FiscalDocumentSnapshot::build(fiscalRecordRow)`), original ids kept:
- F2 local: `order_meta`, `sale_line[]` (by `order_id`), `movement[]` (`order_id`), `transfer_payment` (`order_id`), `outbox[]` (`type='sale' AND order_id`), `session` (row of `order_meta.session_id`), `exchange` (where `new_order_id` = the sale), `customer` (when `order_meta.payment_breakdown` names a local customer created after the previous line — open point O3).
- F2 coupon: same, `movement[]` by `ps_order_id`, `issued_coupon` (leftover voucher id from `payment_breakdown.leftover_voucher.issued_coupon_id`); no `outbox`.
- R5: `refund`, `refund_line[]`, `outbox[]` (`request_id` = refund's upload rows: refund + restock), `session`, `exchange` (by `refund_id`), `order_meta_refunded_amount` (`{"order_meta_id":…, "value":…}` read after commit). The refund's cash movement has no `refund_id` column: it is rebuilt from `refund.cash_amount`, `session_id`, `completed_at` with the concept rule of `RefundService` extracted into one shared function (`RefundService::cashMovementConcept`, reused by both).
- F3: `invoice`.
Sample (shortened):
`{"v":1,"seq":812,"journaled_at":"2026-11-14T18:02:11+01:00","kind":"F2","series":"A26","counter":{"table":"ticket_sequence","letter":"A","year":2026,"number":124},"fiscal_record":{"id":930,"invoice_type":"F2","number":"A26000124","hash":"9C1E…","previous_hash":"77AB…","generated_at":"2026-11-14T18:02:10+01:00",…},"rows":{"order_meta":{"id":1501,…},"sale_line":[…]},"backfill":false,"prev":"5D0F…","line_hash":"E41B…"}`

### D3. Write protocol relative to the MySQL transaction
1. Inside `FiscalRecorder::append` (issuing transaction, `fiscal_chain` locked): run the guard (D7), compute the hash as today, then write an intent `intents/<hash>.json` (`fiscal_record` row + `created_at`, `state:"prepared"`) to the primary, else the secondary; if both fail, log and continue (S2). Then insert the record and update the head as today, and insert one outbox row `type='journal'`, `order_id NULL`, payload `{"number":…, "invoice_type":…, "hash":…}` (D6).
2. After the response (`kernel.terminate` and `console.terminate`), `FiscalJournalFlushListener` (priority above `OutboxSyncListener::onTerminate`, so the upload finds the line) asks `FiscalJournalWriter::flush()`. For each intent of this process it first checks the database by `number` + `hash`: present → `state:"confirmed"`; absent → the transaction rolled back, delete the intent.
3. `FiscalJournalWriter::flush()` (also run by `tpv:cron`): `flock(journal.lock)`; repair the tail (D4); read `head.json`; if the head is not in the database, stop (guard case, never write); select `fiscal_record WHERE id > head.fiscal_record_id ORDER BY id` (ids follow chain order because the chain lock is held from insert to commit), build each line from committed rows only, append with one `fwrite` + `fflush` + `fsync`, update `head.json` atomically (temp + rename, as `CronAttemptMarker`), delete the intent of each line written. Only committed documents ever reach the journal, so the journal is never "ahead" in normal operation.
4. Secondary: when the primary is not writable, step 3 writes to the secondary with the same `seq`. When the primary is writable again, flush copies the secondary's lines after the primary head (each verified by `line_hash` and `prev`) before reading the database, then empties the secondary.
5. Reconciliation rule of `tpv:cron` (`FiscalJournalReconciler::run`): flush; resolve leftover intents older than 2 minutes: in the database → flush journals it; absent and the same number now holds another hash, or the chain head has moved past its `previous_hash` → never issued (moved to `intents/discarded/`); absent and the slot still free → kept, non-blocking, shown in Ajustes after 10 minutes (open point O1); a `confirmed` intent absent from the database → database behind (D7).

### D4. Integrity, truncation and tampering
Reading verifies per line: JSON valid, `line_hash` matches, `prev` equals the previous `line_hash`, `seq` = previous + 1. A last line without `\n` or failing those checks is a torn tail: under the lock the file is truncated to the last valid `\n`, the fragment saved to `quarantine/`, and flush rewrites the document from the database. A failing line that is not the last is tampering or disk damage: state «Diario dañado» (D9), alert e-mail, nothing rewritten, appends go on chained to the last valid line; `tpv:fiscal:journal:verify` names file and line.

### D5. Cost of the guard per issue
At every `append`, under the chain lock already held: read `head.json` (one small file), list `intents/` for `confirmed` entries (normally empty), read `state.json` (cron's shop verdict), one indexed query `SELECT hash FROM fiscal_record WHERE number = ? AND invoice_type = ?` (index `idx_fiscal_record_number`). No cache in memory: per request, well under 1 ms of file I/O plus one primary-index lookup. The same check, without the lock, runs early in `CheckoutService::createOrder`, `RefundService` entry points and `InvoiceIssuer::redeem` so a coupon sale or a refund is refused before PrestaShop is called (`FiscalJournalGuard::assertCanIssue()`).

### D6. Shop copy (module `tpvconnect` 0.9.0)
- Module: front controller `controllers/front/journal.php` (`TpvconnectJournalModuleFrontController`), HMAC as `refunds.php`, rate-limited like it. `POST /module/tpvconnect/journal` body `{"journal_id", "line": {…D2 line…}}` → stores; `POST /module/tpvconnect/journal` body `{"journal_id", "action":"head"}` → `{"journal_id", "last_seq", "series": {"A26": {"number","hash","seq"}, …}}`. Class `classes/JournalStore.php`. Table `PREFIX_tpvconnect_journal` (`id_tpvconnect_journal` PK, `journal_id` CHAR(36), `seq` BIGINT, `series` VARCHAR(16), `number` VARCHAR(60), `invoice_type` CHAR(2), `hash` CHAR(64), `line_hash` CHAR(64), `line` MEDIUMTEXT, `date_add`; UNIQUE (`journal_id`,`seq`), UNIQUE (`hash`)). Idempotency key = (`journal_id`, `seq`, `line_hash`): same → 200 `{"stored":false,"duplicate":true}`; same seq, other `line_hash` → 409. The module verifies `line_hash` before storing (400 otherwise). Created in `install/sql/install.php` and by `upgrade/upgrade-0.9.0.php`; `$this->version = '0.9.0'`; CHANGELOG.
- TPV: `PsJournalClient` (`src/Service/Fiscal/Journal/`), `MIN_MODULE_VERSION = '0.9.0'`. `OutboxSync::process` gains `Outbox::TYPE_JOURNAL = 'journal'` → `processJournal`: finds the line by hash (flushing first if missing), posts it; 404/non-JSON = module too old → row stays pending, next attempt in 1 hour, `state.json` `shop:"unavailable"` (S9); 409 → incident. Rows lost in a restore are re-enqueued by the reconciler when the shop's `last_seq` is below the journal's.
- Shop head: the reconciler calls `head` once per minute, stores `shop-head.json`, and sets the shop verdict in `state.json`: behind when any series' shop `number`+`hash` is missing from `fiscal_record`.

### D7. Guard states (`FiscalJournalGuard`, exception `FiscalJournalBehindException`, HTTP 423)
- `behind_journal`: the journal head (or a confirmed intent) is not in the database.
- `behind_shop`: per D6.
- `journal_missing`: `app_setting fiscal_journal.id` exists but no location has `journal.id` (or it holds another id): blocked until the shop head confirms the database is not behind (the reconciler then re-creates the journal from the database), or `tpv:fiscal:journal:reset --confirm` (A6).
- `ok` otherwise. Journal unwritable is never a block (S2).
POS message (all issuing endpoints): «Caja bloqueada: la base de datos se ha restaurado desde una copia anterior a los últimos documentos. Avisa al administrador (Ajustes → VERI*FACTU → Diario fiscal).» `createLocalOrder`'s catch-all must rethrow this exception, not `localSaveFailed`.

### D8. Replay (`FiscalReplay`, command `tpv:fiscal:replay`)
1. Preconditions: guard state `behind_journal`/`behind_shop`; `flock` on `var/fiscal-replay.lock` and `journal.lock` (flush paused); journal verified (D4) from the line holding the database head. The database head (`fiscal_chain.last_hash`) must equal the `fiscal_record.hash` of some journal line L; otherwise, if the first journal line's `previous_hash` is not in the database → S10 (exit 3). The documents to replay are the lines after L (from the shop copy when the local journal is lost: open point O2). Preflight: every terminal/user referenced exists; every original id to insert is free or holds the identical row; otherwise exit 4 «conflicto» with the table and id.
2. Per document, one transaction, lock order of the code (session → counter → fiscal_chain → stock): `session` (INSERT if missing, as open, then `SELECT … FOR UPDATE`); counter `UPDATE … SET last_number = GREATEST(last_number, n)` (inserting the year row first, as `prepareYear`); `fiscal_chain FOR UPDATE`, check `last_hash` = line's `previous_hash`; insert the document rows with original ids (`order_meta`, `sale_line`, `movement`, `transfer_payment`, `issued_coupon`, `refund`, `refund_line`, `exchange`, `invoice`, `outbox`), `order_meta.refunded_amount` = GREATEST(current, snapshot); insert `fiscal_record` verbatim (id, hash, previous_hash, generated_at, created_at); update `fiscal_chain`. Stock is not touched.
3. Idempotent: a document whose `number`+`hash` is already in `fiscal_record` is skipped; an interrupted run resumes at the first missing line. After the last line, `AUTO_INCREMENT` of every touched table is raised past the restored ids, `FiscalChainVerifier::verify()` must be OK, the guard state is recomputed.
4. Not restored (said in Ajustes and in the guide): Z reports (`z_report`) and closing of cash sessions opened after the backup (they come back open: close them again), print state and `print_job`, stock (`catalog_stock`, the catalog sync reconciles it from the shop), customers created after the backup unless in O3, parked tickets, `audit_log`, `numbering_change`, settings, users, terminals, coupons created with «Crear cupón». Already uploaded sales and refunds are re-queued; the shop deduplicates sales by reference (`ReferencedOrderCreator`) and refunds/restocks by `request_id`.
5. Exit codes: 0 done or nothing to do; 1 error; 2 `--dry-run` (default) found documents to replay; 3 backup older than the journal; 4 conflict. `--apply` executes. Ajustes button: `POST /api/fiscal/journal/replay` (admin, CSRF/origin rules of the other admin endpoints) runs the same service.

### D9. What the administrator sees
`GET /api/fiscal/journal` (admin, `FiscalJournalController`) returns `state.json` + guard state. Ajustes → VERI*FACTU gets a «Diario fiscal» block (`SettingsModal.js`), also summarised in Acerca de → «Estado de la instalación»:
- «Diario fiscal al día: último documento A26000124 (14/11/2026 18:02).»
- «Diario fiscal con {n} documentos pendientes de anotar; se anotan solos cada minuto.»
- «El diario fiscal lleva más de 5 minutos sin poder anotarse. Revisa los permisos de la carpeta backups/fiscal-journal.»
- «La base de datos está por detrás del diario fiscal (falta {número} y {n} posteriores). No se puede vender hasta recuperar los documentos.» + button «Recuperar documentos» (dry-run list first, then confirm).
- «La copia restaurada es anterior al diario conservado (desde {fecha}). Restaura una copia más reciente.»
- «El diario fiscal tiene una línea dañada en {archivo} (línea {n}). Ejecuta tpv:fiscal:journal:verify.»
- «Copia en la tienda al día (último documento {número}).» / the S9 text.
Commands: `tpv:fiscal:journal` (cron job; 0 ok/pending, 1 neither location writable, 2 guard active, 3 journal damaged), `tpv:fiscal:journal:verify` (0/3), `tpv:fiscal:replay [--apply]` (D8.5), `tpv:fiscal:journal:reset --confirm "<motivo>"` (A6). `CronRunner::jobs()` gets `new CronJob('journal', 'Diario fiscal', 'tpv:fiscal:journal')` as the FIRST every-minute job, so the upload that follows finds the lines.

### D10. Retention
No automatic deletion (A4): about 2 KB per document. Rule for manual cleanup in the guide: never delete a month newer than the oldest backup kept, nor younger than four full years (tax records); the shop copy is never deleted by the TPV.

### D11. Provisioning (`FiscalJournalStep`, id `fiscal-journal`, «Diario fiscal preparado»)
`isDone()`: both locations exist with the right permissions and `journal.id` matches `app_setting fiscal_journal.id`. `run()`: create folders; when no journal and no setting exist (first time), write `journal.id`, store the setting, flush with `backfill:true` (documents issued before this feature, rows as they are now). When a journal exists but the setting does not (database restored from before the feature), store the setting and let the guard decide. Never creates a new journal over a lost one (that is A6).
